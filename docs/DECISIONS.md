# Decision log

Decisions made while building the project, including every place the build departs from `docs/PLAN.md` and why. Newest last.

| # | Decision | Why | Consequence |
|---|---|---|---|
| D1 | The acceptance criterion in the brief is cut off ("any recorded decision is fully …"). We read it as **"fully reconstructable and replayable step by step"**. | It is the only reading consistent with the rest of the brief (replay engine, forensic replay UI). | Tested directly: E1 measures how often a recorded decision is fully reconstructed at each level, and `tests/test_core.py::test_full_instrumentation_reproduces_every_decision` checks it at L4. |
| D2 | Synthetic insurance-claims world, no public dataset. | The research questions need ground truth no dataset records: which inputs determined a decision, which violations were injected, and how sources changed afterwards. | External validity is limited to this world and agent (`data/DATASET.md`, `research/REPORT.md` §6). |
| D3 | A rule-and-model pipeline agent, not an LLM agent. | No LLM API key is available in the build environment (see the portfolio registry). The narrative assessor stands in for an opaque external model: non-deterministic, output-only. | The SDK is agent-agnostic (context variables plus tool wrappers), but nothing here shows how it captures an LLM's reasoning. Stated as a limit. |
| D4 | One full trace per decision; levels L0–L4 are projections of it, by event kind (`KIND_LEVEL`) and by field (`FIELD_LEVEL`). | Levels then differ only in what was kept, never in which decisions were made, so comparisons are exact. | Field-level projection matters: at L3 a rule records the random draw it compared, but not the seed, and a model score is recorded without its version; E1 shows what this does to L3 replays. |
| D5 | Module layout differs from the plan: storage is `agentaudit.log` (not `agentaudit.store`) and the agent is `agentaudit.agent` (not `agentaudit.agents.claims`). | One agent and one store did not justify sub-packages. | Names only. |
| D6 | L4 records the agent configuration version, model versions, random seeds, actors and request ids. It does **not** record a hash of the agent's source code, which the plan listed. | The simulation pins code by version (`claims-agent@1.x`), and replay always runs the code it is given. A code hash adds nothing measurable here. | A real deployment should record a code or container digest; the report says so. |
| D7 | E2 runs record-mode replay at every level and live-mode replay once (at L4) per delay, rather than live mode "per level". | Live mode re-queries every input regardless of what was recorded, so its result does not depend on the level. | One live row per delay. |
| D8 | E3 injects **13** violation kinds (11 with checks written for them, 2 held out), attempted on 40% of claims with the kind drawn uniformly. The plan said 10 kinds at 3% per eligible decision. | Uniform attempts at 40% give enough realised cases per kind with 20 seeds. The held-out kinds test what generic checks catch without a check designed for the fault. | Realised counts per kind are reported. Recall on the 11 designed-for kinds is an upper bound; the held-out recall is the honest generalisation number. |
| D9 | E3 reports recall per kind and pooled precision per level, not per-kind F1. | A rule finding is not always attributable to one kind (several checks can fire on one decision), so per-kind precision is ill-defined. | Per-check "on target" and "on clean agent" counts are reported instead. |
| D10 | The faulty agent's fault plan is a pure function of (seed, claim id). | Otherwise its decisions could not be replayed with its own code, and "deployed vs approved code" comparisons would be meaningless. | Replaying the deployed code reproduces faulty decisions; replaying the approved code diverges at the fault. |
| D11 | Wall-clock durations are not recorded in events. | They made the hash chain differ between otherwise identical runs, so `MemoryLog` and `SQLiteLog` could not be checked for identical chains. | E5 measures timing separately. |
| D12 | Tool, external and human outputs are normalised (floats to 10 significant digits) before the agent sees them. | Otherwise a replay from the record could differ from the original in the last bit of a float. | Replays at L4 are exact. |
| D13 | E4 adds `edit_blob` (editing a stored tool output) to the plan's attacks, and "none" is implemented as sequence-number checking. | Tool outputs are stored once as content-addressed blobs; an attacker could target them instead of events. | Eight attacks × four defences. |
| D14 | The console serves one recorded deployment (seed 0, 600 claims, faulty agent). The design's "world/seed selector" is a static label. | Building a deployment takes about a minute and writes a database; doing it from a browser click would make the API write. | `agentaudit demo-db --seed N` records a different deployment. |
| D15 | The console shows simulation ground truth (decision type, injected violation, fraud) beside the record, always dashed and labelled. | It makes the demo legible: you can see what the detector should have found. | Never mixed with recorded data; the Method page says an auditor would not have it. |
| D16 | The tamper lab attacks an in-memory copy of the stored rows; the API never writes to the audit log. | Least privilege: a read-only API cannot damage the evidence. | Tested: the head hash is unchanged after tamper-lab runs (API and UI tests). |
| D17 | Experiment provenance records the commit and marks it `-dirty` when `src`, `configs` or the lockfiles have uncommitted changes. | A first pass of E1–E5 ran with uncommitted API code in the tree; the API does not affect experiments, but the record should say so. | The reported runs were all re-run from one clean commit. |
| D18 | Record-mode first-divergence causes are counted in E1/E2 (added after the first pass). | The first pass showed 85.5% of L3 replays diverging, which needed a cause before it could be reported. | E1 reports the four most frequent first divergent steps per level. |
| D19 | E4 was re-run after a fix to the attack generator (`64ad459`). The first clean run showed the hash chain missing 2% of single-event edits; the cause was the attack, not the chain: halving a zero amount, or setting a decision of "pay" to "pay", left the event unchanged. | A no-op edit is not an attack, and counting it as undetected understated the chain. | `_edit` now always changes the event and refuses to return an unchanged one; a regression test covers it. The superseded run stays in `results/e4_tamper/20261008T062201Z-f561923` for the record; `LATEST` points to the re-run. |
